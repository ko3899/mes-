## 二、业务逻辑梳理摘要

### 2.1 分层架构
```
用户层：admin(管理后台 8081) + frontend(采集终端 8080) —— 原生 HTML/JS
服务层：Flask Blueprint（51 个蓝图 / 8 大业务域）+ services 领域服务（生产/质量/采购/机台）
数据层：SQLite（157 张表，sys_/base_/prod_/inv_/eqp_ 前缀）+ PostgreSQL 兼容层
设备层：AIM TCP Socket + 读码器 + CSV + 边缘网关(HTTPS/MQTT) + MQTT 消费 五路接入
```

### 2.2 核心业务链路（销售→生产→质量闭环）
```
销售订单 → 生产计划 → 批次 → 工单(冻结路线/BOM) → 任务/领料 → 机台准入(AIM L1/L3)
→ 检测报告 → 报工 → 过账；NG 触发 SN 级质量处置闭环(返工补数 / 下一轮 cycle)
```

### 2.3 核心状态机（约 10 套）
- **工单**：0草稿 → 1下达 → 2生产 → 3完工 → 4暂停 → 5关闭 → 6取消
- **报工**：0提交 → 1审核 → 2过账 → 3驳回
- **销售/计划/批次**：共用 5 态
- **出入库单**：0草稿 → 1过账
- **采购单**：0-7 八态
- **质量处置单**：pending_review → approved → task_started → completed（action: rework/scrap/concession）
- 流转逻辑集中在 `production_flow._TRANSITIONS`

### 2.4 权限模型
`login_required`（登录）→ `admin_required`（管理员）→ `permission_required('模块:动作')`（细粒度，从 sys_role.menu_ids JSON 校验）；admin 角色直通放行。权限 key 命名如 `prod:batch:write`、`flow:approve`。

## 三、测试验证结果

### 3.1 自动化测试
- **pytest 全量**：268 passed / 0 failed（375s）
- **本轮修复的 5 个失败用例**（均为安全改动与既有测试的冲突）：

| 用例 | 修复方式 |
|------|----------|
| test_rate_limiter.py ×2 | 压测端点 `/healthz` → `/api/captcha`（限流器改为只统计 /api/ 前缀） |
| test_flow_api.py ×3 | fixture 中给 approver 用户绑定 admin 角色（approve/reject 接口依赖 flow:approve 权限） |

### 3.2 API 鉴权冒烟（本地服务 8080）
7 个业务域接口（dashboard / prod / inv / qm / eqp / sys / notification）未登录访问全部返回 **401**；验证码接口返回 key（SVG 协议）；错误密码登录返回 400 —— 鉴权链路全部符合预期。

### 3.3 本轮修复的线上问题
- **限流器误伤静态资源**（`backend/utils/rate_limiter.py`）：默认 50/hour 对所有请求计数，管理后台一次性加载 30+ 静态资源即触发 429"请求过多"。已修复为**仅对 `/api/` 前缀接口计数**，静态资源不再计入；压力验证 30 次静态请求全 200、API 正常。
