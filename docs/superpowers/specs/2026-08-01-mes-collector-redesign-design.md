# MES 采集终端完整改造设计

日期：2026-08-01  
状态：待用户最终审阅

## 1. 目标与边界

本阶段面向车间操作员、质检员和物料领用人员，把现有 `/` 单文件采集终端改造成适合扫码枪、手机和 420×800 桌面壳长期使用的工业手持终端。改造同时覆盖企业蓝视觉、个人业务口径、条码识别、摄像头扫码、断网暂存和安全渲染。

保留 Flask、SQLite、原生 HTML/CSS/JavaScript、`mes_collector_app.py` 与 PyWebView 打包方式。不引入 Vue、React 或大型 UI 库，不改变现有业务单据的含义。确有必要时可以增加只读查询参数或小型查询接口，但不得破坏现有接口调用方。

## 2. 技术方向

采用已确认的 B 方案：将 `frontend/index.html` 拆成轻量应用骨架，并在 `frontend/static/` 下按样式令牌、API、状态、离线队列、扫码器、共享视图和业务页面划分原生模块。模块通过明确的全局命名空间或 ES 模块接口协作，继续由 Flask 直接提供静态资源，无构建步骤。

页面保持六个业务入口：首页、扫码、我的任务、报工、质检和物料。生产看板不与采集端混装，作为后续独立阶段实现。

## 3. 视觉与应用骨架

采集端采用“工业手持终端”风格，并继承管理后台 B 方案的语义色：

- 深海军蓝 `#0B1F3A` 用于顶栏与稳定框架，主操作蓝使用 `#2563EB`。
- 工作区使用浅灰蓝 `#F3F6FA`，卡片使用白色与清晰边框；成功、警告和危险使用克制的绿、琥珀与红。
- 顶部显示站点/终端标题、当前用户、网络状态和待上传数量。
- 底部固定六项导航，当前页同时通过图标、文字和强调色表达；安全区适配带底部手势条的手机。
- 主按钮与扫码输入高度至少 48px，普通点击区域至少 44px；表单在 360×600、420×800 与 390×844 下无需横向滚动。
- 页面切换使用 120–180ms 克制过渡，并遵循 `prefers-reduced-motion`。

登录页不再预填默认密码。登录成功后恢复上次业务入口；会话失效时清理敏感状态并返回登录页。所有加载、空数据、失败、成功和权限不足反馈使用应用内组件，不再调用浏览器原生 `alert`。

## 4. 页面与业务行为

### 4.1 首页

首页只呈现当前登录用户的待完成任务、当天报工数量和与其操作相关的待处理事项。统计接口必须明确使用当前会话用户和服务器当天日期，不能把全厂最近 100 条记录冒充个人今日数据。首页提供扫码报工、生产报工、质量检验和我的任务四个大尺寸快捷入口。

### 4.2 扫码

扫码入口统一接收 USB 扫码枪、键盘输入和摄像头识别结果。解析器支持：

- 以 `WO` 开头的工单号；
- 以 `TK` 开头的任务号；
- 产品条码或产品编码，通过后端精确查询产品并展示关联的可报工任务。

未知码、无匹配、重复触发和网络失败必须给出不同反馈。扫码枪快速输入通过单一生命周期监听器处理，离开页面后解除监听，避免重复绑定。摄像头优先使用浏览器原生 `BarcodeDetector`；浏览器或 PyWebView 不支持时隐藏摄像头按钮并保留扫码枪/手工输入，不加载外部 CDN 库。

### 4.3 我的任务与报工

“我的任务”只返回 `assigned_to` 为当前用户的任务；管理员不因角色而自动看到全部任务。任务卡展示工单、产品、工序、计划、完成、状态和进度，可执行开始与报工。

报工表单校验合格数、不良数、任务剩余量和必填关联字段。提交过程中禁用按钮，防止重复提交。后端业务校验失败时保留用户输入并显示具体原因。

### 4.4 质检与物料

质检页区分待检记录与新建检验，不把已检记录放入“待检”列表。提交后刷新当前列表并给出单据号。

物料页必须明确区分物料库存与工具借用。现有 `/api/tool/borrow/add` 只用于工具借用，界面文案不得称其为物料领用；库存查询继续使用 `/api/inv/balance/list`。如果本轮没有真实物料出库接口，则入口命名为“库存/工具”，不伪造物料领用能力。

## 5. 离线队列与同步

只有可安全重放、带客户端唯一操作 ID 的写请求可以进入离线队列。本阶段覆盖生产报工与已确认可幂等化的采集写操作；开始任务等非幂等或缺少冲突策略的操作在离线时禁用并说明原因。

队列使用浏览器本地持久化存储，记录操作类型、请求体、创建时间、重试次数和最后错误。网络恢复或用户点击“立即同步”时按创建顺序提交：

- 成功或服务端确认同一操作 ID 已处理：移除队列项；
- 网络错误或 5xx：保留并采用有上限的退避重试；
- 4xx 业务校验失败：停止自动重试，标为“需要处理”，允许用户查看原因并删除或重新编辑。

顶部网络状态必须显示在线/离线、待同步数量和失败数量。退出登录不自动删除未同步业务数据，但再次登录为不同用户时禁止读取或上传前一用户的队列。

## 6. 安全与异常处理

- 所有来自条码、用户输入和 API 的动态文本通过 `textContent` 或统一转义工具渲染；禁止直接拼入 `innerHTML`。
- API 层统一处理非 JSON 响应、超时、401、业务错误和网络错误，并返回稳定结果结构。
- 登录表单不得包含默认生产凭据；敏感信息不得写入本地持久化存储。
- 摄像头在用户主动点击后才请求权限；关闭扫码页、切换标签或页面隐藏时立即停止媒体轨道。
- 弱网或离线状态不得显示虚假的成功结果。

## 7. 测试策略

先写失败测试，再实现最小代码使其通过。Node 测试覆盖条码解析、HTML 转义、个人任务/今日统计映射、扫码监听器生命周期、离线队列状态机和 API 错误归一化；Python 测试覆盖个人任务过滤、个人今日统计、产品码查询和幂等写接口。现有 Python 与 Node 测试必须全部保持通过。

浏览器验收覆盖登录、六项导航、扫码枪输入、摄像头能力降级、任务开始、在线报工、模拟断网排队、恢复同步、质检和库存查询。验证视口为 360×600、420×800 与 390×844，并检查控制台无阻断性错误。

## 8. 验收标准

- 采集端与管理后台形成统一但适合手持操作的企业蓝视觉语言。
- 六个入口均有真实数据或明确的能力边界，不存在“功能开发中”占位。
- 我的任务与今日统计使用当前用户和当天口径。
- 工单、任务和产品码可被识别；摄像头不支持时有无故障降级。
- 已纳入离线协议的写操作可排队、恢复上传并处理业务失败，不重复生成业务记录。
- 所有动态文本安全渲染，重复进入扫码页不会累积事件监听器或摄像头资源。
- 自动化回归和三种目标视口浏览器验收全部通过。

## 9. 非目标

- 不开发 Android/iOS 原生应用。
- 不接入第三方云扫码、推送或消息服务。
- 不为没有后端业务语义的按钮伪造成功流程。
- 不在本阶段改造生产看板或管理后台。
